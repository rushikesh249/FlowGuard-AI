1. PROJECT OVERVIEW
--------------------------------------------------------------------------------
FlowGuard AI is an AI-powered enterprise process intelligence and workflow
analytics platform designed to discover process flows, detect operational
anomalies, and provide explainable AI insights for Procure-to-Pay (P2P) financial
workflows.

Purpose & Core Philosophy:
Unlike conventional fraud detection systems that rely on rigid predefined rules
or require manually labeled fraud datasets, FlowGuard AI learns how an
organization's business processes normally operate directly from raw historical
event logs. It identifies unusual process executions, operational bottlenecks,
and workflow deviations, presenting them through an interactive web dashboard
with human-readable, rule-based and statistical explanations.

Core Technical Stack:
- Frontend: Next.js 16, React 19, TypeScript, Tailwind CSS, Recharts, React Flow
- Backend: FastAPI, Python 3.11, Pydantic, SQLAlchemy, Alembic
- Process Mining: Pure pandas Directly-Follows Graph (DFG) engine
- Artificial Intelligence / ML: scikit-learn (Isolation Forest), custom explainers
- Background Task Queue: Celery 5.6.3 with Redis 7 broker
- Relational Database: PostgreSQL 15
- Containerization: Docker Compose orchestration

3. SYSTEM ARCHITECTURE
--------------------------------------------------------------------------------
Containerized Service Topology (docker/docker-compose.yml):

1. frontend (docker-frontend-1)
   - Technology: Next.js 16 (App Router), React 19, TypeScript, Tailwind CSS
   - Port Mapping: 3000:3000
   - Role: User interface, authentication state, interactive React Flow process
     visualization, Recharts analytics dashboards, and report export UI.

2. backend (docker-backend-1)
   - Technology: FastAPI (Python 3.11), SQLAlchemy, Pydantic, Alembic
   - Port Mapping: 8000:8000
   - Healthcheck: curl -f http://localhost:8000/health (interval 5s, timeout 5s)
   - Role: REST API server, JWT authentication, XES parser/validator, process
     mining computation engine, report generation, and task dispatch.

3. postgres (docker-postgres-1)
   - Technology: PostgreSQL 15
   - Port Mapping: 5432:5432
   - Volume: pgdata -> /var/lib/postgresql/data
   - Role: Persistent relational store for users, uploads, and anomaly run metadata.

4. redis (docker-redis-1)
   - Technology: Redis 7 (alpine)
   - Port Mapping: 6379:6379
   - Healthcheck: redis-cli ping (interval 5s, timeout 3s)
   - Role: In-memory message broker and result backend for Celery task execution.

5. worker (docker-worker-1)
   - Technology: Celery 5.6.3 (Python 3.11, scikit-learn, pandas)
   - Port Mapping: None (internal network communication with Redis/PostgreSQL)
   - Role: Asynchronous background execution of feature engineering (11 dimensions
     across 251,734 cases) and Isolation Forest model training/scoring.

Key Architectural Justifications:
- Isolation Forest Algorithm: Operates by isolating anomalies via random feature
  splits. In financial workflow graphs where deviations (e.g. out-of-order steps,
  bypassed approvals) produce distinct structural anomalies in feature space,
  Isolation Forest efficiently detects outliers without requiring labeled data.
- Fresh Training Per Dataset: Rather than relying on a static, globally pretrained
  model that carries cross-company distribution bias, FlowGuard AI trains the
  Isolation Forest fresh on each uploaded dataset. This tailors the anomaly scoring
  baseline strictly to the specific organization's operational profile.
- Asynchronous Celery Worker: Extracting 11 features and training an Isolation
  Forest on 251,734 traces takes ~1.5 to 2 minutes. Offloading training to Celery
  ensures FastAPI request threads never block, returning an HTTP 202 Accepted
  immediately with a trackable run ID.


4. IMPLEMENTATION STATUS BY MODULE
--------------------------------------------------------------------------------
Module 1: Authentication & RBAC (Implemented)
- User registration (POST /auth/register), JWT login (POST /auth/login), and
  password reset (POST /auth/reset-password) using bcrypt password hashing.
- Role-Based Access Control (RBAC) supporting three roles: Admin, Manager, Analyst.
- Role claim embedded directly in JWT payload.
- Dependency-level role gating via require_roles(Role.Admin, Role.Manager).
- Tenancy Model: Single-tenant enterprise workspace where datasets, process
  graphs, anomaly runs, and reports are shared organization-wide.
- Permission Matrix:
  * Admin: Full read/write (upload datasets, trigger training, view analytics)
  * Manager: Full operational read/write (upload datasets, trigger training, view analytics)
  * Analyst: Organization-wide read-only (view dashboards, explore graphs, browse
    anomalies, export reports; write actions return HTTP 403 Forbidden).

Module 2: Data Ingestion & Validation (Implemented)
- Upload endpoint (POST /upload/xes) accepting IEEE 1849-2016 .xes XML files.
- Ingestion validator checking mandatory attributes (concept:name, time:timestamp,
  org:resource, case attributes), parsing ISO-8601 timestamps, sorting traces,
  and removing duplicate records.
- Generates a deduplicated, cleaned CSV (1,415,010 events) for downstream engines.
- Lists shared organization upload history (GET /upload/history).

Modules 3 & 4: Process Mining & Workflow Explorer (Implemented)
- Pure pandas Directly-Follows Graph (DFG) discovery engine (backend/process_mining.py)
  constructing adjacency transition matrices without PM4Py counting bugs.
- Per-activity statistics: event count, first/last occurrence, average transition
  duration, median transition duration, 90th percentile delay (p90_duration_seconds),
  resource counts mapping ({resource: count}), and department affiliations.
- Case activity sequence lookup (GET /process-mine/case/{case_id}).
- Interactive frontend visualization (/process) built on React Flow with pan/zoom,
  node detail side-drawers, and a client-side transition-frequency slider filtering
  edges from maximum frequency down to 1 transition.

Modules 5 & 6: AI Anomaly Detection Engine (Implemented)
- Feature Engineering (backend/ai/features.py): Computes 11 case-level features:
  1. n_events (integer volume of activities)
  2. n_unique_activities (distinct activity types)
  3. duration_seconds (total case throughput time)
  4. repetition_count (total duplicate activity instances)
  5. has_rework (binary flag for repeated activity loops)
  6. max_step_duration (maximum transition time between consecutive events)
  7. avg_step_duration (mean transition time across all events)
  8. n_unique_resources (number of distinct users/resources involved)
  9. n_unique_departments (number of distinct spend areas involved)
  10. has_weekend_activity (binary flag for events recorded on Saturday/Sunday)
  11. has_approval_step (binary flag for presence of PO approval activity)
- Model: scikit-learn IsolationForest(contamination=0.05, n_estimators=100, random_state=42).
- Anomaly scoring: Decision function normalized to 0.0-1.0 anomaly score and
  confidence score (|score - threshold| / max_distance).
- Endpoints: POST /anomaly/train (dispatches Celery job, returns 202),
  GET /anomaly/status/{run_id}, GET /anomaly/runs, GET /anomaly/results/{run_id}.

Module 7: Explainable AI Engine (Implemented)
- 8 pluggable explainers in backend/ai/explainers/ combining heuristic domain
  rules with statistical outlier detection:
  * Rule-Based Explainers:
    1. skipped_approval: Flagged if PO is created/paid without approval activity.
    2. payment_without_po: Flagged if invoice/payment occurs before PO creation.
    3. out_of_order: Flagged if standard P2P progression is inverted.
    4. duplicate_activity: Flagged if critical approvals/orders execute multiple times.
    5. unusual_case_length: Flagged if case activity count is outside 1st-99th percentile.
  * Statistical Explainers:
    6. duration_anomaly: Flagged if case duration exceeds dataset mean + 2.5 standard deviations.
    7. resource_anomaly: Flagged if resource count exceeds 3x dataset average or uses batch users.
    8. event_count_anomaly: Flagged if total steps exceed dataset mean + 2.5 standard deviations.
- Composite severity score computed on a standardized 0 to 10 scale.
- Endpoints: GET /explanations/{run_id} and GET /explanations/{run_id}/case/{case_id}.

Module 8: Analytics Dashboard (Implemented)
- Frontend dashboard (/dashboard) featuring 10 integrated widgets:
  1. Total Cases KPI Card (251,734 traces)
  2. Normal Workflows KPI Card (95.0% / 239,151 cases)
  3. Flagged Anomalies KPI Card (5.0% / 12,583 cases)
  4. Unique Activities KPI Card (42 event types)
  5. Average Processing Time KPI Card (weighted mean cycle duration)
  6. Process Health Score KPI Card (95/100)
  7. Anomaly Score Distribution Histogram (5 score buckets with crimson highlights)
  8. Run Status & Model Metadata Card (algorithm, contamination, start/end timestamps)
  9. Monthly Activity & Anomaly Trend (dual-layer AreaChart across 46 months)
  10. Department Delay & Anomaly Rates Table (136 departments ranked by delay/anomalies)
  11. Top Vendors by Volume & Spend Table (vendor case count, total spend EUR, anomalies)
  12. Approval Bottleneck Analysis Card (average delay, p90 delay, approver distribution)
  13. Flagged Anomalies Table (top 10 severe cases with drill-down links)

Module 9: Enterprise Report Generation (Implemented)
- 4 comprehensive report types built in backend/reports/generator.py:
  1. Executive Summary: High-level KPIs, health score, activity volume, risk summary.
  2. Department Report: Department breakdown, case counts, mean durations, anomaly rates.
  3. Anomaly Report: Detailed breakdown of flagged cases, severity scores, and explanations.
  4. Monthly Trend Report: Time-series event volume, case throughput, and anomaly counts.
- Dual-format export: Professional PDF (fpdf2) and CSV export for all 4 types.
- Backend JSON data feeds: GET /reports/data/department/{id}, /reports/data/monthly/{id},
  and /reports/data/vendors/{id}.

Module 10: AI Assistant (Designated Stretch Goal - Not Implemented)
- In accordance with docs/PRD.md (Module 10 designated as an optional stretch goal),
  the natural language conversational assistant was not implemented in this version.


5. AUDIT & VERIFICATION HISTORY
--------------------------------------------------------------------------------
During the rigorous audit-fix pass, all identified architectural, performance,
and frontend gaps were systematically corrected and verified live:

Issue 1: Anomaly Report I/O Performance Bottleneck
- Finding: Anomaly report generator executed single-row disk reads in a loop (O(N)
  file I/O), causing multi-minute generation times on the 251k-case dataset.
- Fix: Refactored generator to load case events in memory from a single DataFrame
  pass and pre-compute dataset-level baseline statistics once.
- Verified Benchmark Result: Generation time dropped from 10.5571s to 0.2698s (~39x speedup).

Issue 2: Incomplete Role-Based Access Control (RBAC)
- Finding: JWT tokens lacked role claims, and write endpoints (/upload/xes,
  /anomaly/train) lacked role-based dependency gating.
- Fix: Encoded Role in JWT on login, implemented require_roles dependency factory,
  and gated write endpoints for Admin and Manager roles.
- Verified Result: Live HTTP requests confirmed Analyst receives real HTTP 403
  Forbidden on upload/train, while Admin and Manager receive HTTP 201/202.

Issue 3: Missing Frontend Authentication Pages
- Finding: User registration and password reset were only accessible via raw API calls.
- Fix: Created /register (with role selection) and /reset-password pages in Next.js,
  and added navigation links on the login page.
- Verified Result: Full browser-based registration, login, password reset, and re-login.

Issue 4: Tier A Dashboard Enhancements
- Finding: Dashboard lacked an Average Processing Time KPI card, and the process
  graph lacked edge-filtering controls for dense workflows.
- Fix: Added Average Processing Time KPI card (computing weighted transition duration)
  and implemented a client-side React Flow threshold slider in /process.
- Verified Result: Graph slider dynamically filtered edges from 498 down to 1 transition.

Issue 5: Backend JSON Report Endpoints & Count Reconciliation
- Finding: Frontend charts lacked dedicated JSON data endpoints; initial queries
  showed minor count discrepancies.
- Fix: Added /reports/data/department, /reports/data/monthly, and /reports/data/vendors.
  Reconciled 1,415,010 cleaned events across 46 months (100.0% of cleaned dataset) and
  added an "Unassigned" department bucket for 3,289 null-department cases.
- Verified Result: All department cases sum to exactly 251,734 traces (100.0% coverage).

Issue 6: Tier B Dashboard Widgets & Data Structure Alignment
- Finding: Approval bottleneck resource distribution expected a {resource: count}
  dictionary, while the process mining engine returned a flat list, causing NaN shares.
  Also, p90_duration_seconds was not previously computed.
- Fix: Added resource_counts dictionary (top 50 by frequency) and p90_duration_seconds
  to ActivityStats, while preserving the flat resources list for /process backward compatibility.
- Verified Result: Approver bars render real non-zero share percentages (e.g. user_603: 27%).

Issue 7: Organization-Wide Shared Dataset Access
- Finding: Legacy single-user ownership checks (uploaded_by == user.id) in 5 router
  files prevented Analysts from viewing datasets uploaded by Admins.
- Fix: Removed single-user silo checks from anomaly, process_mining, reports, upload,
  and explanations routers, establishing organization-wide dataset sharing while
  strictly maintaining role-based write permissions.
- Verified Result: Analyst successfully loads shared uploads, process graphs, anomaly
  results, and reports created by Admin/Manager.

Issue 8: Docker Clean-State End-to-End Verification
- Finding: Need to confirm the entire application starts cleanly from an empty volume
  without depending on stale database records or cached container layers.
- Fix: Executed docker compose down -v, rebuilt all containers, ran fresh Alembic
  migrations (4 versions), and executed the multi-role test suite.
- Verified Result: All 5 containers reached healthy status; full P2P lifecycle passed.

7. KNOWN LIMITATIONS AND OUT-OF-SCOPE ITEMS
--------------------------------------------------------------------------------
1. Single-Tenant Architecture:
   - FlowGuard AI is designed as a single-tenant enterprise platform. All
     authenticated users belong to the same organizational domain and access a
     shared data pool. Multi-tenant database schema partitioning is out of scope.

2. Supported Ingestion Format (.xes Only):
   - The platform exclusively ingests IEEE 1849-2016 .xes XML files. Generic flat
     CSV upload is out of scope because standard CSVs lack standardized hierarchical
     trace-to-event relationships, lifecycle transitions, and trace-level attributes.

3. Role Permissions Parity (Admin & Manager):
   - Admin and Manager roles share identical operational write permissions
     (both can upload datasets and trigger ML training runs). Analysts hold read-only
     permissions. Finer-grained administrative separation is not in scope.

4. Concurrent Dashboard Query Latency on Unindexed Large Datasets:
   - On the full 1.415M event log, concurrently querying all 5 dashboard data
     endpoints from cold disk takes ~74 to 80 seconds without in-memory Redis
     response caching. This is an operational characteristic of large-scale pandas
     aggregations on raw CSVs, noted as a future caching opportunity.

5. Pre-2018 Timestamp Outliers in Source Data:
   - 318 events carry historical timestamps (dating back to 1948) due to legacy
     source PO references in the BPI Challenge 2019 dataset. They represent 0.0225%
     of events and do not impact core 2018-2019 process mining discovery.

6. Module 10 (AI Assistant):
   - Designated as an optional stretch goal in docs/PRD.md; not implemented.
